What to inspect

1 · Header and provenance

Confirm the result, environment, run ID, tool version, and scope note before interpreting any check. This prevents a local sample from being mistaken for a production health claim.

2 · A test card

Open a card to see the request, tags, HTTP status, latency, attempts, assertion paths, bounded response preview, and—when a check fails—a redacted curl reproduction command.

3 · Filters and downloads

Search by test, tag, or assertion; filter failures or retries; sort by latency; then download JSON or JUnit for automation and CI viewers.

4 · The intentional failure path

The failure report deliberately covers status, JSON, header, latency, and retry failures. Expected-versus-actual values show the next debugging question without contacting a real service.

Reproduce it locally

From the repository root, start the fixture, validate without network requests, then write all three artifacts:

python3 -m qa_sentinel serve-demo
python3 -m qa_sentinel validate examples/demo-suite.json
python3 -m qa_sentinel run examples/demo-suite.json \
  --html /tmp/qa-sentinel-report.html \
  --json /tmp/qa-sentinel-report.json \
  --junit /tmp/qa-sentinel-report.xml

Run examples/failure-suite.json for the failure-first example. It exits with status 1 by design, while still writing useful diagnostics.
